# 2026-08-19 박원형 멘토 멘토링 — 네이티브 쿼리 라이브 리뷰 예고, 기술 채택은 측정 뒤에

> [!tldr]
> **다음 멘토링(9/7 19:00 온라인)은 네이티브 쿼리에 초점을 맞춘 라이브 코드 리뷰다.** 그때까지는 구조를 건드리지 말고 기능 구현을 끝내라는 것이 멘토의 요구다. 준비물은 네이티브 쿼리 사용 패턴과 빈도 요약이고, 리뷰는 IntelliJ Ultimate로 한다.
> **기술 채택은 측정이 먼저다.** Kafka·CQRS를 근거 없이 먼저 들인 것을 짚었고, Redis Cluster 같은 관심 기술도 성능·가용성 테스트에서 문제가 드러난 뒤에 붙이라고 했다. 그러려면 **목표 사용자 수**부터 정해야 한다.
> 나머지 큰 줄기 셋: **일정은 예상의 1.5~2배로** 잡아 번아웃을 피할 것, **AI가 짠 코드는 내재화**할 것(면접에서 설명해야 한다), **엔티티에 비즈니스 로직과 검증을 넣어** 서비스 계층 과부하를 줄일 것.

## 이 노트로 답할 수 있는 질문
- 다음 멘토링은 언제이고 무엇을 준비해야 하나?
- 네이티브 쿼리에 대한 멘토 입장은 무엇이고 우리 ADR과 어떻게 다른가?
- 새 기술(Kafka·CQRS·Redis Cluster)을 언제 도입해야 하나?
- DDD에 대해 어떤 타협을 권했나?
- 일정과 작업량에 대해 무슨 조언이 나왔나?
- 이 회의에서 나온 작업 항목은 무엇인가?

> [!note] 출처의 성격
> 녹음·전사가 아니라 **AI가 생성한 회의 요약 원문**이다(강정민 전달). 발언 뉘앙스나 정확한 표현은 원문 이상으로 복원할 수 없고, 회의 일자도 원문에 없어 수령일로 잡았다.

## 참석
멘토 박원형 · 조성민 · 최규호 · 강정민 (부산 17기)

## 1. 네이티브 쿼리 — 다음 세션의 주제
멘토는 JPA 안에서 네이티브 SQL을 폭넓게 쓰는 것을 **유지보수 위험**으로 보고 최소화를 권했다. 구체적 제안은 둘이다.

- 데이터베이스 기능을 **유틸리티 계층으로 추상화**한다
- 가능한 자리는 JPQL이나 애플리케이션 수준 로직(쿼리 여러 번)으로 바꾼다

성민이 "네이티브가 많은데 리팩터링해야 하나"를 먼저 꺼냈고, 정민이 조회와 생성 양쪽에 폭넓게 쓰인다고 확인했다. 멘토는 **일부는 피할 수 없다는 것도 인정**했고, 과거에 네이티브 쿼리로 겪은 유지보수 어려움을 근거로 들었다.

> [!warning] 우리 ADR과 부딪히는 지점
> [[ADR 영속 계층 JPA 유지 MyBatis 반려]]는 "네이티브 약 50곳은 ORM의 한계가 아니라 **PostgreSQL 전용 기능**(ON CONFLICT upsert · PostGIS · advisory lock)을 쓰려는 것"이라 판정했다. 멘토의 "JPQL로 바꿔라"는 그 사유에 해당하지 않는 쿼리에는 맞지만, 전용 기능 쿼리에는 적용되지 않는다.
> **9/7 리뷰 준비물이 곧 이 대조표다** — 쿼리마다 "전용 기능이라 불가피" / "JPQL 전환 가능" / "유틸로 추출 가능"을 갈라 두면 리뷰가 판정으로 바로 간다.

**합의**: 지금 구조를 미리 바꾸지 않고 다음 세션의 라이브 리뷰에서 개선 기회를 찾는다. 진행 중인 작업을 방해하지 않기 위해서다.

## 2. 기술 채택 — 측정이 정당화한다
멘토는 새 기술을 넣기 전에 **핵심 서비스 구현을 끝내라**고 했다. 기술 선택은 취향이 아니라 성능·가용성 테스트에서 확인된 필요가 이끌어야 한다.

- 성민이 Redis Cluster를 해보고 싶다고 했고, 서비스와의 관련성은 스스로 인정했다
- 정민은 **Kafka와 CQRS가 명확한 필요 없이 들어온 것**에 우려를 냈다
- 멘토는 CQRS를 "쿼리 서비스와 커맨드 서비스를 분리하는 것"으로 풀어 설명하고 실용적인 구현 방법을 제시했다
- 전제 조건: **목표 사용자 수를 먼저 정의**해야 성능 테스트와 운영 규모 산정이 가능하다

## 3. DDD — 완전 채택 대신 실용적 타협
멘토는 도메인 엔티티와 지속성(JPA) 엔티티를 **분리**하는 쪽을 권했지만 둘을 합치는 일반적 관행도 인정했다. 지금 단계에서 DDD를 완전히 채택하기 어렵다는 점을 스스로 짚으며 타협안을 냈다.

- JPA 엔티티 안에 **비즈니스 로직과 유효성 검증을 넣어** 서비스 계층 과부하를 줄인다
- **단순 세터 대신 의미 있는 메서드**를 노출해 엔티티 동작을 캡슐화한다
- 나중에 완전한 DDD로 옮기는 것은 어렵다

이 두 항목은 레포 컨벤션과 이미 같은 방향이다(`@Setter` 지양, `Video.markBlinded()` 같은 상태 전이 메서드).

## 4. 일정과 작업량
- API 연결이 반복 수정으로 예상보다 길어져 지연이 생겼다(성민). 웹은 거의 끝나 API 수정만 남았고(규호), 앱은 UI 디자인 단계이고 API 연동은 시작 전이다.
- 다른 팀보다 한 달 늦은 압박 + 주간 스프린트가 스트레스원으로 나왔다.
- 멘토 권고: **예상 소요를 1.5~2배로 잡는다.** 완벽한 완료는 비현실적이고, 포트폴리오로서의 품질을 지키려면 탈진을 피해야 한다.

## 5. AI 지원 개발
간단한 수정도 AI 처리 시간 때문에 수동보다 오래 걸리는 경우가 있다는 관찰이 나왔다. 멘토의 요구는 **AI가 만든 코드를 개발자가 완전히 이해할 것** — 특히 면접에서 자기 코드를 설명해야 하기 때문이다. 이미 익숙한 코드에는 AI를 선택적으로만 쓰라고 했다. 정민은 팀이 핵심 코드와 쿼리는 직접 검토한다고 확인했다.

## 6. 데모에서 나온 것
- 규호가 격자에 묶인 영상 업로드·재생을 시연했다
- 정민이 인기 장소 수동 입력과 공공데이터 시딩을 설명했고, 성민이 행정 구역 처리와 좌표 범위 매핑을 설명했다
- 멘토는 역지오코딩 카카오 API 통합과 UI 디자인을 긍정 평가했다
- 겹치는 위치 영역 관리, 추천 경로·포토스팟 표시 방식을 함께 논의했다

## 7. 모바일 UI
앱은 Figma 디자인 단계이고 구현 대기다. 멘토는 웹의 넓은 기능을 좁은 모바일 화면에 넣는 어려움을 짚으며 사용성을 신중히 보라고 했다. 팀은 익숙함을 위해 **네이버 맵의 칩 컴포넌트**를 참고한다.
