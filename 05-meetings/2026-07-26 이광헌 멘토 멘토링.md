# 2026-07-26 이광헌 멘토 멘토링 — AI 개발 프로세스·PRD·스킬 분해

> [!tldr]
> 핵심 피드백 3축: ① **PRD 먼저** — 목적·기능·비기능·시퀀스/클래스 다이어그램·변경 파일까지 담는 설계 문서를 잘 만들고, PRD 생성 스킬·템플릿을 만들 것. ② **스킬은 잘게** — 큰 스킬 금지, 쪼개서 서브에이전트 오케스트레이션(Spec-Driven-Dev), 오케스트레이션 규칙을 Rule에 명시. ③ **AI 산출물 검증 체계** — AI가 짠 코드 품질을 점수화(SWE-bench 채점 기준 참고)하고 테스트 커버리지도 뽑을 것.
> 제품 측: 블러 처리는 **수요가 있는지부터 확인**하라. 마케팅(스레드·릴스)은 한 글로 끝내지 말고 연재로.
> 운영 팁: 남는 토큰은 자는 시간에도 돌려라 · 어려운 개념은 HTML 시각화로 학습 · 사람용 자료와 AI용 컨텍스트를 구분하라. 지라 티켓도 AI 생성과 비교해보고 더 나으면 채택 — 단 AI가 해결한 흐름은 사람이 기억하고 있어야 함.

## 이 노트로 답할 수 있는 질문
- 이광헌 멘토가 제안한 PRD 구성 요소는?
- 스킬·서브에이전트 운용에 대한 피드백은?
- AI가 짠 코드의 품질을 어떻게 검증하라고 했나?
- 블러 기능에 대한 제품 관점 피드백은?
- 마케팅·포트폴리오 관련 조언은?
- llm-wiki에 대해 어떤 질문을 받았나?

## 주요 논의
### 1. 설계 문서(PRD) 우선
- PRD를 먼저 잘 만들어라 — 구성: 목적·목표, 기능/비기능 요구사항, 시퀀스 다이어그램, 클래스 다이어그램, 어떤 파일이 바뀌어야 하는지, 문제 상황.
- 만들기 전 전체적으로 생각하는 research 조사 → 기능·비기능 쭉 뽑기.
- 우선 클로드에게 PRD를 만들게 하고, 나오는 양식으로 템플릿·PRD 생성 스킬을 만들 것.
- 요즘은 문제 발생도 지라로 들어옴 — 지라에서 PRD까지 이어지는 흐름.

### 2. 스킬 분해·서브에이전트 오케스트레이션
- 스킬 하나가 크면 안 됨 — 다 쪼개라(Spec-Driven-Dev). 서브에이전트 여러 개로 오케스트레이션.
- 오케스트레이션 방식을 Rule에 적어둘 것. 코드리뷰 + 정적분석 결합.
- 빌드 오류도 손으로 하지 말 것: 디버깅 포인트 삽입 → 리뷰 → Code Implement → Test 루프.

### 3. AI 산출물 검증
- 개발을 AI가 해주면 **AI가 얼마나 잘하는지 검증 체계**가 있어야 함 — 만족할 코드 품질 기준을 정하고 점수화.
- SWE-bench(swebench.com)가 어떤 기준으로 채점하는지 참고. 카파시 가이드라인 언급.
- 테스트를 뽑고 있으니 커버리지(%)도 함께.

### 4. 제품·마케팅
- 블러 처리는 수요 확인부터 ([[AI 블러 파이프라인 실측 현황]] 개선 논의와 연결).
- 스레드·릴스 마케팅: 한 글로 끝내지 말고 연재 — "대학생 3명이 의미 있는 포트폴리오를 고민하며 써보고 있습니다" 톤.

### 5. 팀 운영
- 스토리 포인트: 이번 주 20개쯤 추가했으니 다음 스프린트부터 에스티메이트 반영.
- 지라 티켓 리뷰 시간에 다른 도메인 팀원도 알 수 있게 공유. FE는 티켓에 이미지·GIF 첨부.
- 스프린트 요약: 완료 전 각자 한 일 보고 시간.
- llm-wiki: 왜 도입했고 어떤 효과를 봤는지 설명 요청받음 — Agents에 최우선 등록해 cursor·claude code·codex가 참조.
- 남는 토큰은 자는 시간에도 돌아가게 · 어려운 기술은 HTML 시각화로 학습 · 사람용 자료 / AI용 컨텍스트 구분.
