# 2026-08-01 신기용 멘토 멘토링 — 취업 관점 이력서·포트폴리오 리뷰

> [!tldr]
> 취업(백엔드) 관점 이력서·포트폴리오 리뷰. 판정은 명확했다 — **지도(PostGIS)·영상 처리·AI 기능은 서비스 백엔드 지원에선 변별력이 없고**, 살릴 것은 **Redis 하나를 깊게**(센티널 vs 클러스터 → 실습 → 마스터 kill → 페일오버 다운타임 실측 → WAS 대처를 비즈니스 관점까지 서술)다.
> 신규 추천 2개: **대규모 알림 서비스**(배치 발송·스로틀링·중복 방지)와 **관측성**(부하테스트 사이클 + Prometheus/Grafana → LGTM 스택). 뻔한 키워드(인덱스·N+1·쿼리 튜닝·기술 스택 나열)는 버리고, Redis+Lua 동시성 처리는 면접에서 털리니 비추천.
> 원칙: 프로젝트는 1~2개만 깊게, 프로젝트당 어필 피처 1~2개. **직접 실습 없이 이력서에 쓰지 않는다.** 실무 노하우로 공공 API는 직접 의존하지 말고 배치 수집→정제 테이블→정제본으로만 응답하는 구조를 권함.

- 멘토가 신규로 추천한 주제 2개와 그 이유는?
- 이력서에서 버려야 할 뻔한 키워드는 무엇인가?
- Redis + Lua 동시성 처리가 왜 위험한가?
- 공공데이터를 실무에서 어떻게 다루라고 했나?
- "AI 활용 경험" 면접 질문에 어떻게 답해야 하나?

## 주요 논의

### 1. 무엇을 버리고 무엇을 살릴 것인가
- **취업 목표부터 명확히**: 서비스 퀄리티를 높이는 것과 취업용 경쟁력은 다르다. 지금은 "취업에 최적화된 것"을 할 시기.
- **지도(PostGIS)**: 네이버/카카오 지도처럼 해당 도메인에 지원하는 게 아니면 변별력 없음. "운전면허 있다고 운전 잘한다고 보지 않는 것"과 같다.
- **동영상 처리**: 서비스 백엔드 지원 기준으로 어필이 안 된다.
- **AI 기능(사진 민감정보 블러 등)**: "AI 돌려서 기능 제공"만으로는 의미 없음 — 비즈니스 관점 또는 서버(스프링) 쪽에서 풀어낸 이야기가 있어야 한다.
- **버릴 불릿**: 기술 스택 나열, 버전 업그레이드 서술, 요구사항 정리·문서화 툴 나열("없는 게 더 세련됨"), "합의 조율로 해결" 류 의미 불명 항목. S3 Presigned 다이렉트 업로드는 나쁘진 않으나 우선순위 낮음.
- **표현 교정**: "FastAPI 파일 서버" → **MSA 환경의 서비스 간 통신** 관점으로 서술.

### 2. Redis — 유일하게 "살릴 것"으로 지목 (핵심)
- 클러스터 vs 센티널 차이를 공부하고 **직접 실습**. 회사에선 클러스터가 사실상 기본 스택.
- 마스터–레플리카 구성에서 **마스터를 죽여 슬레이브 승격(페일오버)을 실험**.
- 페일오버 **다운타임 동안에도 요청은 들어온다** — WAS·세션 처리에서 어떻게 대처하도록 설계했는지를 **비즈니스 관점까지 포함해 서술**하는 것이 가장 중요.
- 흐름: 공부 → 클러스터 실습 → 마스터 kill → 페일오버 검증 → 서비스 관점 서술. (구체 실습안은 [[백엔드 학습 로드맵 Redis HA·알림·관측성]] 트랙 1)

### 3. 신규 추천 — 대규모 알림 서비스
- "알림 보내기"는 재미있고 확장성이 좋아 살릴 가치가 있는 주제.
- 실시간 개별 발송 vs 대량 발송 구분, **배치 처리**(예약 시각 기준 적재 후 배치 발송 — 회사 실무 방식).
- **스로틀링/분산 발송**: 한 번에 다 쏘면 알림 받은 사용자가 동시에 몰려 서버가 죽는다 → 5~10분에 걸쳐 나눠 발송.
- 발송 중복 방지 로직, 데이터 관리 방안까지 묶어 "대규모 알림 서비스" 컨셉으로.

### 4. 신규 추천 — 모니터링·관측성
- 부하 테스트(k6)를 "해봤다" 수준이면 의미 없음. **부하 테스트 → 병목 확인 → 개선 → 재테스트** 사이클이 핵심.
- **Prometheus + Grafana**로 관측하되, Grafana가 시각화만 하면 한계 — slow query 등 **원인 추적**까지 가야 한다.
- **LGTM 스택(Loki·Grafana·Tempo·Mimir)** 등 트렌드 키워드를 공부하고 실제로 붙여볼 것. 구축해 보이면 매우 좋다.
- "API는 만들고 끝이 아니라 운영·유지보수 관점에서 관측해야 한다"는 스토리가 좋은 어필. 면접관이 모르는 최신 개념이 나오는 것도 (진짜 해봤다면) 플러스 — 단 막히면 즉시 들킨다.

### 5. 이력서 키워드 잔소리
- 커넥션 풀 설정·인덱스·쿼리 튜닝: **너무 뻔하다.** "인덱스 없어서 느렸다 → 잡으니 빨라졌다" 전개가 뻔히 보인다. 차라리 Redis 스토리 하나를 제대로.
- N+1: 정답이 이미 나와 있어 변별력 없음.
- 블루그린 배포: 좋은 소재.
- **Redis + Lua 스크립트 동시성 처리 = 비추천**
  - Lua는 컴파일 타임 체크가 없어 런타임에 터진다. 스프링 코드 사이에 Lua가 끼면 실수 여지·재사용·트래킹 모두 나빠진다.
  - WAS는 여러 대인데 Redis 마스터는 사실상 한 대 — 연산을 Redis에 몰면 **부하가 한 곳에 쏠려 장애 포인트**가 된다. Redis는 가볍게 쓰고 로직은 WAS에서.
  - 이 꼬리 질문에 제대로 답한 지원자를 거의 못 봤다.

### 6. 공공데이터 실무 노하우
- 공공 API는 **스펙(컬럼·필드)을 예고 없이 바꾼다.** 실시간 직접 의존은 장애를 그대로 맞는 구조.
- 회사 방식: ① 배치로 **원본(raw) 그대로 적재** → ② 별도 배치로 **우리 포맷 정제** → ③ 사용자 요청은 **정제 데이터로만 응답**.
- 공공데이터 서비스가 "OO 기준 일시"를 표기하는 이유가 이것. 신입도 이 운영 관점을 알고 말할 수 있으면 좋다. (FillMap zone 데이터도 같은 구조 — [[zone 상권 공공데이터 근거]])

### 7. 프로젝트 개수·깊이 원칙
- 사이드 프로젝트는 **1~2개만 깊이 있게**. 기능이 많다고 깊은 게 아니라 **기능 하나에 고민을 많이 붙인 것**이 깊이.
- 프로젝트당 어필 피처 1~2개면 충분 — 면접에서 어차피 다 못 말한다. 화면 보여주기용(뷰잉) 기능은 취업에 도움 안 됨.
- 2년 전 채팅 프로젝트 재활용은 비추천. 새로 한다면 **한 달 안에 "채팅" 하나만**, 어필 포인트는 대용량 메시지 처리·동시 접속 시 메시지 오더링 보장. 더 나은 선택은 **현 소마 프로젝트에 채팅을 붙이고** 과거 경험을 녹이는 것.
- 과거 시점 그대로 말하지 말고 "이때 이렇게 했는데 최근 다시 발전시켰다"로.
- 면접관이 소스코드를 따로 보나? → **거의 안 본다.**

### 8. "AI 활용 경험" 답변법
- "써봤다/안 써봤다"가 아니라: **AI로 생산성을 높였다 + AI가 짠 코드를 한 줄씩 뜯어보며 몰랐던 걸 배웠다**로 관점을 돌린다.
- 에이전트를 직접 만들었으면 그 얘기를, 아니면 MCP·스킬 활용, AI 코드 리뷰에서 배운 점 중심으로.
- 회사처럼 데이터·유즈케이스가 많은 환경의 에이전트와 개인용(사용자가 본인뿐)의 차이도 인지하고 말할 것.

### 9. 협업·팀 운영
- 역할을 기계적으로 나눌 필요 없다. 같이 합의하며 하거나, 각자 해본 뒤 공유하거나 둘 다 좋다 — 같은 걸 각자 해보면 막힌 지점을 물어보며 빈틈을 채우고, 그래야 면접에서 경험으로 말할 수 있다.
- AI로 결과만 뽑아 제출하면 꼬리 질문에 대답이 안 나온다.
- **각자 키워드 하나씩 잡고 공부한 뒤 서로 공유(발표)** 하는 방식 추천.
- 백엔드 외 직군(프론트 등)은 멘토가 도울 게 없으니 무리해서 참석할 필요 없음.
