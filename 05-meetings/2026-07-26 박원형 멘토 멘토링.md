# 2026-07-26 박원형 멘토 멘토링 — 레이어별 스킬·queryDSL·CQRS 분리

> [!tldr]
> AI 운용: 커밋 메시지에서 authored by 빼기 · **서비스 layer별로 스킬을 분리**(레이어별 검증·커밋, toDto·Repository 따로) — 한 덩어리는 이해 병목. **티켓 하나의 제작 플로우를 HTML 위키로 상세히 남길 것**(데이터 저장 위치·실행된 쿼리·ExceptionHandler 동작 시점·빈 동작).
> API 설계: **BE가 FE 친화적으로 내려줘라** — 연관관계 없는 데이터 조인엔 jpaRepository만으로 부족할 수 있음 → **queryDSL projection**이 좋은 대안.
> 구조 제안: jpaRepository는 POST/PUT만, GET은 queryDSL 쿼리로 — **commandService/queryService 분리(CQRS)**. 단, jpaRepository만으로 가능한지도 함께 고민해볼 것.

## 이 노트로 답할 수 있는 질문
- 박원형 멘토가 제안한 스킬 구성 방식은?
- 티켓 플로우 위키에 담으라고 한 내용은?
- FE 친화적 API를 위해 어떤 기술을 권했나?
- command/query 분리 제안의 구체적 형태는?
- queryDSL을 언제 쓰라고 했나?

## 주요 논의
### 1. AI 운용·문서화
- 커밋 메시지에서 authored by 제거.
- 서비스 layer별로 스킬을 따로 둘 것 — 레이어별로 검증하고 커밋(toDto·Repository 따로따로). 한 번에 다 보는 건 이해의 병목.
- 티켓 하나의 플로우(만드는 과정)를 HTML로 변환해 위키에 상세히 남길 것: 데이터 저장 위치, 실행된 쿼리, ExceptionHandler 동작 시점, 빈(Bean) 동작 방식.

### 2. FE 친화적 API — queryDSL
- BE가 FE에게 친화적으로 API를 내려줄 것.
- 연관관계 없는 데이터들을 조인할 때 jpaRepository만으론 부족할 수 있음 → queryDSL(projection으로 커스텀)이 좋은 대안.

### 3. CQRS식 분리 제안
- jpaRepository는 POST·PUT만 처리, GET은 queryDSL 쿼리로만.
- commandService / queryService 분리.
- 반론 숙제: jpaRepository만으로 할 수 있는지도 고민해볼 것.
