# 2026-08-08 김민수 멘토 멘토링 — 지도·격자 시스템 (EPSG:5179 전환의 발단)

> [!tldr]
> 멘토의 핵심 권고 한 줄: **위경도(EPSG:4326)를 상수로 나눠 100m를 근사하지 말고, EPSG:5179 평면좌표로 투영한 뒤 100으로 나눠라.** 위경도 1도의 지상 거리가 지역마다 달라 서울·부산에서 같은 상수로는 정사각형이 성립하지 않는다는 이유다.
> **이 권고는 같은 날 채택·구현됐다** → [[ADR 격자 계산 EPSG5179 전환]] (MSG-347, BE PR #134). 이 노트는 그 결정의 **입력 기록**이고, 확정된 내용·기각 대안·마이그레이션은 ADR이 정본이다. 전날 준비한 [[지도·공간 데이터 설계 멘토 설명용]] §10의 질문 15개가 이 자리의 안건이었다.
> 격자 외 조언은 대체로 현행과 정합한다: Grid ID ↔ 표시명 분리, FE/BE 계산 정합성 검증(샘플 200개 대조), 뷰포트 요청을 격자 범위로 정규화해 캐시 적중률 높이기, 줌 아웃은 **BE 1차 압축(H3) + FE 2차 클러스터링** 2단 구조(이번 티켓에서는 기각·유예), 지도·검색 provider 혼용 시 POI 좌표 오차 인지, AI는 **설계 세션과 구현 세션을 분리**.

## 1. 격자 계산 — EPSG:5179 투영 권고 (핵심)

**문제 제기**: 위경도는 각도 단위라 1도의 실제 거리가 지역마다 다르다. 위도 방향은 비교적 일정하지만 경도 방향은 위도가 높을수록 짧아진다. 부산 기준으로 맞춘 경도 차를 서울에 그대로 쓰면 칸의 크기·형태가 달라진다. 멘토는 현재 화면의 격자가 "부산 영역 위에 격자 패턴을 그린 뒤 행정구역으로 잘라낸 시각화"에 가까울 가능성도 지적했다.

**권장 흐름**:
```
GPS (EPSG:4326 lat/lng)
  ↓ ST_Transform  (PostGIS)
EPSG:5179 (x, y / meter)
  ↓
gridX = floor(x / 100)     gridY = floor(y / 100)
```
```sql
ST_Transform(ST_SetSRID(ST_MakePoint(longitude, latitude), 4326), 5179)
```
```java
gridX = Math.floorDiv((long) x, 100);
gridY = Math.floorDiv((long) y, 100);
```

**좌표 저장**: 원본 4326(지도 표시·외부 API 연동)과 투영 5179(거리 계산·격자 판정)를 함께 관리. 서버와 클라이언트가 **좌표계·격자 원점·격자 크기·반올림 방식·경계 좌표 처리 규칙** 5가지를 하나라도 다르게 쓰면 FE가 그린 격자와 서버 판정이 어긋난다.

> [!note] 이후 전개
> 이 권고는 그대로 채택돼 MSG-347로 구현됐다([[ADR 격자 계산 EPSG5179 전환]]). ADR이 추가로 규명한 것: 새 셀이 위경도 축과 평행하지 않아(자오선 수렴 최대 약 1.6°) **FE 렌더가 Rectangle→Polygon, 뷰포트 범위가 2점→4점**으로 바뀐다는 파생 효과, 그리고 grid_id 포맷·API 계약·표시명 규칙은 불변이고 값만 교체된다는 점(V28이 원본 좌표에서 전량 재계산).

## 2. FE 격자 렌더링과 정합성 검증
- BE가 격자선을 만들어 내려주는 것보다 **FE가 현재 Viewport 기준으로 계산**하는 편이 반응성에 유리하다(변환 연산 자체는 가볍다). 흐름: 지도 이동 → Viewport → 4326→5179 → 필요한 Grid 범위 계산 → 격자선 생성 → 5179→4326 → Naver Map Polyline.
- FE는 `Proj4` 계열 라이브러리로 변환. **계산은 5179, 렌더링은 4326.**
- **정합성 검증 절차(권고)**: BE에서 Grid 샘플 약 200개 생성 → 좌표·Grid ID 추출 → 동일 입력으로 FE 계산 → `gridX`·`gridY`·Grid ID·격자 시작/끝 좌표가 전부 일치하는지 대조.
  → 팀은 같은 목적을 언어 중립 픽스처(`zone-naming.json`, [[zone 표시명 FE 계약]])로 이미 하고 있었다. 이 권고의 실질은 **샘플 규모를 200건으로 키우는 것**이고, ADR도 FE 작업 시점에 이 픽스처로 검증하도록 남겨 뒀다.

## 3. Grid ID와 표시명
- **방법 A** `gridX`/`gridY` 그대로(또는 `12345_67890` 문자열) — 위치 복원·이웃 탐색·디버깅이 쉬움. 단 문자열 키는 정수보다 저장·인덱스 비용이 큼.
- **방법 B** 단일 정수 ID로 인코딩 — 키·인덱스가 작지만 복원 규칙 설계가 필요하고 복잡도가 오름.
- 멘토 권고: **초기에는 `gridX`,`gridY` 복합(유니크) 키가 가장 관리하기 쉽다.** (단일 정수 ID 안은 ADR에서 기각 대안으로 보존됐다.)
- **실제 Grid ID와 사용자 표시명은 분리하라** — ID에 지역명을 넣지 말고 별도 alias/display name으로. 지역 할당은 가장 가까운 POI/지역 연결 → 지역 내부 정렬 → 번호 부여(`서면 A-14`, `건대 3번 타일`). 여러 지역에 걸치면 중심점 거리·겹침 비율·지역 우선순위로 하나 선택.
  → 현행 zone 설계([[ADR 격자 표시명 zone]])와 방향 일치.

> [!note] 표기 주의
> 규호 버전 §9는 Grid ID를 `gridX_gridY`로 적었지만 실제 구현은 **`gridY_gridX`** 순서다. 정리 과정의 표기 착오이니 인용 시 주의.

## 4. 지도 이동 시 조회 전략
- 지도가 조금 움직일 때마다 요청하는 것 자체는 문제 아님. 다만 **Bounding Box → Grid ID 범위로 정규화**하면 동일·유사 범위의 캐시 적중률이 올라간다. 잦은 요청은 debounce 또는 "현 위치에서 재검색" UX로 제한.
- API가 반드시 위경도를 받을 필요는 없다 — FE가 Viewport의 Grid 범위를 계산해 **Grid ID 범위로 요청**해도 된다.

## 5. 줌 레벨별 데이터·클러스터링
- 줌 아웃 상태에서 100m 격자를 전부 내려주는 건 비효율. 축척에 따라 표현을 바꾼다: **시/군/구 집계 → H3 집계 → Grid 집계 → 개별 마커**. 줌 레벨별로 다른 엔드포인트(`/points/by-region`, `/points/by-h3`, `/points/by-grid`)를 두는 방법도 있다 — 하나의 API가 모든 줌을 처리하게 만들지 말 것.
- **2단 클러스터링**: BE가 화면보다 조금 촘촘한 단위로 1차 압축해 대표 좌표 + count만 내려주고(`{latitude, longitude, count}`), FE가 지도 SDK 클러스터링으로 2차로 묶으며 count를 합산한다.
- **H3는 저장용 기본 격자가 아니라 조회·집계용 보조 인덱스로** 쓰는 게 적절하다(서비스의 사각 격자와 모양이 달라서). → MSG-347에서는 즉시 도입을 기각·유예했다.
- 화면 동시 표시 객체는 **약 100개(10×10 Grid)를 기준선**으로 잡고 성능을 측정하라. 특정 줌 레벨 숫자를 절대 기준으로 삼지 말고 축척·Viewport 크기·데이터 밀도·Web/Mobile 성능으로 판단.

## 6. 지도 provider 선택
- 네이버·카카오 지도는 각자 내부 좌표 보정이 있어 **그 지도 안에서 표시하는 일반 서비스라면 문제없다.** 측량·등기급 정확도가 필요하면 VWorld 같은 정밀 지도가 적합.
- 다만 **표시·검색·지오코딩을 서로 다른 사업자로 섞으면 위치가 조금씩 어긋난다.** 특히 지하철 출구·버스정류장·건물 출입구·작은 POI에서 문제가 될 수 있다. 정합성이 중요하면 provider 통일 고려.
  → 현행은 지도 네이버([[ADR 지도 SDK 네이버 전환]]) + 검색 카카오([[ADR 장소 검색 카카오 로컬 프록시]]) 혼용이며, provider 통일은 MSG-347에서 기각 대안으로 보존됐다.

## 7. React Native / Expo
- RN이 Flutter보다 GPS 정확도가 본질적으로 떨어진다고 보기 어렵다(결국 Native API를 쓴다). 기본 라이브러리가 부족하면 그 부분만 Native Module로 구현 가능.
- Expo로 Android·iOS·Web 빌드 타깃을 한 프로젝트에 둘 수 있지만, **Web과 App의 UI 구조가 다르면 자동으로 통합되지 않는다.** 이미 Web React + App RN으로 상당 부분 구현했다면 **지금 스택 전면 변경은 비용 대비 이득이 크지 않다.**

## 8. AI로 복잡한 기술을 구현할 때
- 한 세션에서 조사·설계·구현을 다 하면 초기 판단이 틀렸을 때 잘못된 방향으로 전체가 진행된다. **세션을 분리하라.**
  1. **설계 세션**(강한 모델): 좌표계·원점 결정, Grid ID 규칙, 서버/클라이언트 역할 분리, 예외·테스트 케이스, Implementation Instruction 작성
  2. **사람의 설계 검토**
  3. **구현 세션**: 확정 명세 기준 코드 생성
- 지도·좌표계 작업에서는 **BE 변환 코드 + Grid 샘플 200개 + 요구사항**처럼 **검증 가능한 입출력 데이터를 함께 제공**하는 것이 정확도를 크게 높인다.
